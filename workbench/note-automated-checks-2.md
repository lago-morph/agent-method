The specification from which `implementations/2/verify.js` can be
regenerated by an agent with no other context, and the decisions made
while writing it. The script is derived from this note, not the other
way round; when they disagree, this note is corrected first and the
script regenerated. The guide for notes of this kind is
[note-test-method-definition.md](note-test-method-definition.md).

Implementation 2 covers two use cases, so the checks cover both:
[use-case-initial-ui.md](use-case-initial-ui.md) and
[use-case-edit-ideas.md](use-case-edit-ideas.md).

## Environment and harness

- **Runtime:** Node.js with Playwright and a Chromium build (any recent
  version; 1.56.1 and Node 22 were used). WebKit is preferred whenever
  it can be installed, because the target is Safari; Chromium is the
  stand-in, and the gap is stated in the report.
- **Loading:** the implementation file is opened over `file://` from the
  script's own directory, exactly as the user opens it. No server, no
  bundling, no copying.
- **Viewports:** two browser contexts, iPad landscape 1024 × 768 and
  iPad portrait 768 × 1024, both with touch enabled and mobile emulation
  on. Every check runs in both; a check that passes in one and fails in
  the other fails the run.
- **Errors:** a page-error listener is installed before navigation; any
  uncaught script error fails the run and is printed.
- **No test framework.** One plain script, no dependencies beyond
  Playwright, mirroring the implementation's own no-dependency rule.
- **Two sequences per orientation**, separated by a fresh page load:
  sequence A exercises the Initial UI use case, sequence B the Edit
  ideas use case. They share one browser context and one page; the
  reload gives sequence B a known starting state.

## Hooks the implementation must expose

The checks locate elements by these ids and classes. They are part of
the contract between the implementation and the checks: an
implementation regenerated from the spec must expose them, or the checks
must be regenerated with it.

| Hook | Meaning |
| --- | --- |
| `main > .pane` | the three panes, in order left, middle, right |
| `#left`, `#middle`, `#right` | the left pane, the idea list area, the idea edit area |
| `#ideas li` | one row per idea, in display order |
| `#ideas li.empty` | a row showing the "(empty)" placeholder |
| `#ideas li.placeholder-title` | a row whose shown line stands in for a missing title |
| `#ideas li.selected` | the selected row |
| `#text` | the text control holding the selected idea's literal text |
| `#new`, `#undo`, `#redo` | the New, Undo, and Redo controls |
| `#load-test-data` | the load-test-data control |

Rows are found by their exact visible text when a specific test idea is
needed; that is why test-data titles are stable.

Two hooks changed shape from implementation 1, because the idea text
area became editable:

| Hook | Implementation 1 | Implementation 2 |
| --- | --- | --- |
| `#text` | a `div`; its content is read with `textContent` | a `textarea`; its content is read with `value`, and it is disabled when no idea is selected |
| the edit area's scroller | `#right` (the pane) | `#text` (the control fills the pane and scrolls itself, so the browser can keep the insertion point in view) |

## Sequence A — the Initial UI use case

State carries from one step to the next, so the order is part of the
specification. Expected counts follow from the test data set
([note-test-data-2.md](note-test-data-2.md)): 19 ideas per load (15
short, 1 wide, 1 large, 1 empty, 1 whitespace-only), with the empty idea
created before the whitespace-only one within a load. Each check is a
named boolean; the name states the expected fact, so a failing name
reads as the broken sentence.

implementation 2 onwards, selecting away from an idea with no visible
content deletes it, so any check that selects a placeholder changes the
row count for everything after it. Keeping those steps last preserves
the counts (19 and 57) that implementation 1 used, so the two runs stay
comparable.

## Sequence B — the Edit ideas use case

The page is reloaded, then the test data is loaded three times, so the
list overflows the pane and "stays visible" is a real check. 57 rows at
the start; the New command adds one, giving 58.

| # | Step | Check | Source |
| --- | --- | --- | --- |
| 1 | reload, click load three times | (setup: 57 rows) | |
| 2 | click New | `newGivesEmptySelectedInTopGroup`: 58 rows; the selected row has class `empty` and text "(empty)"; every row before it is also `empty` | Edit ideas, New ideas |
| 3 | " | `newIsEditableAndFocused`: `#text` is the active element, is not disabled, and its value is empty | Edit ideas, insertion point ready |
| 4 | scroll `#middle` to its bottom, then type "Aardvark" | `listFollowsTypingImmediately`: exactly one `.selected` row, its text is "Aardvark", and it is no longer `empty` | Edit ideas, the list follows the text |
| 5 | " | `movesToItsAlphabeticalPosition`: the non-empty rows are in order, and every remaining `empty` row is before the selected one | Edit ideas, moves immediately |
| 6 | " | `selectedRowStaysVisible`: the selected row's box lies within `#middle`'s box | Edit ideas, list scrolls to keep it visible |
| 7 | undo once | `undoRevertsMostRecentChange`: `#text` value is empty and the selected row is `empty` again | Edit ideas, Undo |
| 8 | redo once | `redoReappliesUndoneChange`: value is "Aardvark" | Edit ideas, Redo |
| 9 | type "\nA second line." | `secondLineDoesNotChangeTitle`: the selected row's text is still "Aardvark" | Initial UI, first line is the title |

| 12 | redo 40 times | `redoReachesLatestText`: value is "Aardvark\nA second line." | Edit ideas, Redo |
| 13 | redo 3 more times | `furtherRedoDoesNothing`: value unchanged | Edit ideas, redoing further does nothing |
| 14 | undo once, put the caret at the end, type "!", redo once | `newChangeDiscardsRedo`: the value after the redo equals the value right after typing "!", and differs from the value at step 12 | Edit ideas, a new change discards the redo |
| 15 | " | `undoNeverChangesOtherIdeas`: still 58 rows | Edit ideas, undo touches only this idea |
| 16 | click the first "Banana bread" row, caret to offset 0, press Enter | `blankFirstLineShowsNextLine`: exactly one `.selected` row; its text is "Banana bread"; it has class `placeholder-title` and not `empty` | Edit ideas, blank first line |
| 17 | " | `blankFirstLineSortsByThatLine`: the non-empty rows are still in order | same |
| 18 | click "mango sorbet", select all, press Backspace | `emptiedIdeaShowsPlaceholderButRemains`: still 58 rows; value empty; the selected row is `empty` | Edit ideas, deleting happens only on leaving |
| — | screenshot `b1-editing` | | |
| 19 | undo once | `momentarilyEmptyKeepsItsHistory`: value is "mango sorbet" again and still 58 rows | Edit ideas, its undo history is intact |
| 20 | redo once, then click "lighthouse tour" | `emptiedIdeaDeletedOnLeaving`: 57 rows | Edit ideas, deleted on leaving |
| 21 | click New, then click the selected row again | `reselectingSameIdeaDeletesNothing`: 58 rows; exactly one `.selected` row and it is `empty` | Edit ideas, re-selecting is not leaving |

Rows named by text are taken as `nth=0` of the matching rows, because
three loads put three copies of each test idea in the list. Ordering
among equal titles is creation order, so `nth=0` is always the copy from
the first load, and the same row is found again after it is edited.

## Output contract

- One JSON object on standard output: `{ landscape: { check: boolean, …
  }, portrait: { … } }`, with an `errors` array added to an orientation
  only when script errors occurred.
- Then one line, `PASS` or `FAIL: ` followed by the failed check names as
  `orientation.check`, then one line naming the screenshot directory.
- Exit code 0 on pass, 1 on any failure.
- Screenshots go to the directory given as the first argument, or a fresh
  temporary directory; never into the repository.
- The script's header comment carries the run command:
  `NODE_PATH="$(npm root -g)" node verify.js [output-dir]`.

## Decisions made while writing the checks

- **The environment decisions of implementation 1 are repeated
  unchanged:** Playwright with Chromium (the only engine installed),
  loading over `file://` from the script's directory, both iPad
  orientations with touch and mobile emulation, exact expected counts,
  location by ids and classes with test ideas found by exact title,
  named booleans with a JSON body and a PASS/FAIL line, screenshots kept
  outside the repository, the page-error listener installed before
  navigation, a fresh browser context per orientation, and a run by hand
  before delivery. Their reasons are in
  [note-automated-checks-1.md](note-automated-checks-1.md) and are not
  restated here.
- **Two sequences rather than one.** Deletion on leaving changes the row
  count of every later step, and the editing checks need a known
  starting state. Reloading the page between the two sequences keeps
  sequence A's counts identical to implementation 1's, so results stay
  comparable, and keeps sequence B's arithmetic short enough to follow.
- **The keyboard, not the buttons, drives Undo and Redo in the checks**
  (`Control+z`, `Control+Shift+z`). Both routes run the same function,
  and the keyboard route additionally proves that the platform shortcut
  is intercepted rather than reaching the text control's own history.
  The buttons are exercised at the checkpoint by hand.
- **The insertion point is placed with `setSelectionRange`, not by
  clicking in the text.** Where a click lands depends on the font and
  the viewport; an offset does not, so the checks stay deterministic.
- **Undo and redo are pressed 40 times where the check is "all the way
  back".** The number only has to exceed the number of entries the
  typing produced (8); pressing more is how "undoing at that point does
  nothing further" gets exercised at the same time.
- **`undoRevertsMostRecentChange` is a check of the coalescing rule.**
  Typing "Aardvark" and undoing once returns the text to empty, not to
  "Aardvar", because a run of characters typed at the insertion point is
  one change ([note-implementation-structure-2.md](note-implementation-structure-2.md)).
  If that rule is revised, this check is revised with it.
- **The caret-visibility check measures the scroller, not the caret.**
  A textarea gives no API for the caret's position, so the check scrolls
  the control back to the top with the caret at the end, types, and
  requires that what remains below the visible area is no more than the
  bottom padding plus one line. That is the observable consequence of
  keeping the insertion point in view, and it fails cleanly if the
  control does not scroll at all.
- **The on-screen keyboard is not checked.** Headless Chromium has none;
  the behavior is listed as a checkpoint row in
  [note-acceptance-criteria-2.md](note-acceptance-criteria-2.md).
- **Copy, cut, and paste are not driven.** The use case says the
  platform's own facilities are used and the application adds none; that
  is checked by inspecting the implementation for clipboard code, not by
  a script.

## Regenerating the script

1. Read the use cases the implementation record includes and the record
   itself; draft the acceptance-criteria table.
2. For each row, write one or more named boolean checks; keep the two
   sequences above (or a new one that is written down before coding).
3. Confirm the hooks table against the implementation; add hooks to the
   implementation rather than locating by position.
4. Run at every viewport the record's environment implies; review the
   screenshots once; report results faithfully.
