The specification from which `implementations/4/verify.js` can be
regenerated by an agent with no other context, and the decisions made
while writing it. The script is derived from this note, not the other
way round; when they disagree, this note is corrected first and the
script regenerated. The guide for notes of this kind is
[note/test-method-definition.md](test-method-definition.md).

Implementation 4 covers two use cases as revised on 2026-09-06, so the
checks cover both: [use-case/initial-ui.md](../use-case/initial-ui.md)
and [use-case/edit-ideas.md](../use-case/edit-ideas.md).

## Environment and harness

Unchanged from implementation 3
([note/automated-checks-3.md](automated-checks-3.md)): Node.js with
Playwright and Chromium (1.56.1 and Node 22 were used); WebKit
preferred but not installed; the file loaded over `file://` from the
script's own directory; two browser contexts, iPad landscape
1024 × 768 and portrait 768 × 1024, both touch-enabled with mobile
emulation; every check runs in both; a page-error listener installed
before navigation; one plain script, no test framework, no dependency
beyond Playwright; two sequences per orientation separated by a fresh
page load; three inspection checks read the implementation's source
text and are reported once, outside the two orientations.

## Hooks the implementation must expose

| Hook | Meaning |
| --- | --- |
| `main > .pane` | the three panes, in order left, middle, right |
| `#left`, `#middle`, `#right` | the left pane, the idea list area, the idea edit area |
| `#ideas li` | one row per idea, in display order |
| `#ideas li.empty` | a row showing the "(empty)" placeholder for a blank idea |
| `#ideas li.selected` | the selected row |
| `#ideas li`'s `data-id` attribute | the idea's stable id, for locating one specific idea once editing can move it relative to identically-titled siblings (see below) |
| `#text-wrap` | the box the right pane's two layers occupy together |
| `#text` | the interactive layer: a textarea holding the selected idea's literal text, transparent text and background, caret and native selection visible; disabled when no idea is selected |
| `#text-display` | the non-interactive display layer: shows the same text with a soft hyphen (U+00AD) inserted wherever a word is split for display |
| `#new`, `#undo`, `#redo` | the New, Undo, and Redo controls |
| `#load-test-data` | the load-test-data control |
| `#messages` | the message area, full width, below the panes |
| `#message-text` | the current message's text; empty when there is none |
| `#message-dismiss` | the message's × ; `hidden` when there is no message |
| `#message-list-button` | the button that opens and closes the message list |
| `#message-list` | the message list panel; `hidden` when closed |
| `#message-entries li` | one row per message, newest first; **no row at all** when there are none |
| `.message-time`, `.message-body` | the time and the text within a message row |
| `#message-list-close` | the message list's own × |

Rows are found by their exact visible text when the text is unique in
the current state; test-data titles are stable for that reason. Where
several ideas share a title (three loads put three copies of every
test-data title in the list, and this implementation's two "Same first
line" ideas share one by design), a row named by text is taken as
`nth=0` of the matching rows for a *first, unedited* lookup — ordering
among such rows is still creation order, because they are still
identical in their entire content. Once a check has edited one such
idea, comparing entire content (this implementation's own change; see
"Decisions made while writing the checks") can move it relative to its
still-identical siblings, so a check that must find that exact idea
again reads its `data-id` right after first selecting it and locates it
by `#ideas li[data-id="…"]` from then on, never by text.

Changes from implementation 3's hooks:

| Hook | Implementation 3 | Implementation 4 |
| --- | --- | --- |
| `#message-entries li.none` | the "No messages" placeholder row shown when the list is empty | removed — the use case now says the list opens empty, so there is no row, placeholder or otherwise, to find |
| `#text` | the sole element in the right pane: an ordinary textarea, its own text visible | now the interactive layer only: same textarea, same value and events, but its text and background are made transparent (see `#text-display`) |

| `#text-wrap` | did not exist | new: the box `#text` and `#text-display` both occupy |

## Decisions made while writing the checks

- **Implementation 1 through 3's environment and mechanics are repeated
  unchanged**, per [note/automated-checks-3.md](automated-checks-3.md)
  and its own predecessors: Playwright with Chromium, loading over
  `file://`, both iPad orientations, exact expected counts, location by
  ids and classes, named booleans with a JSON body and a PASS/FAIL
  line, screenshots outside the repository, a page-error listener
  installed before navigation, a fresh browser context per orientation,
  two sequences separated by a reload, the keyboard rather than the
  buttons driving Undo and Redo, the insertion point placed with
  `setSelectionRange`, and a run by hand before delivery.
- **Editing an idea can move it relative to identically-titled siblings,
  because ordering now compares entire content.** This was found while
  writing the "history cleared on selecting another" check
  (step 33): with three loads, three identical "Quantum garden" copies
  exist; typing "zzz" onto one changes its entire content, so it no
  longer ties with (and no longer necessarily sorts adjacent to) its
  two untouched siblings — `#ideas li:has-text("Quantum garden")
  >> nth=0` could then find a *different* "Quantum garden" than the one
  just edited, once its position moved. The check first reads the
  target idea's `data-id` right after selecting it, and re-locates it
  by that id from then on. This is a genuine behavioral consequence of
  the use case's own change (see
  [note/implementation-structure-4.md](implementation-structure-4.md)),
  not a quirk of the checks, so any check anywhere that edits an idea
  and must find that *exact* idea again — as opposed to "any unedited
  copy of this title" — needs the same care. Steps 22–23 and 28–30 also
  edit identically-titled ideas, but never need to *re-find* the edited
  one by text afterward, so they were left as they were.
- **The word-splitting checks measure the display layer's text for a
  soft hyphen, never a visual line count.** U+00AD is a real character
  in `#text-display`'s `textContent` whether or not it is currently the
  point of a break, which is enough for "was this word offered a split
  opportunity" — but a check for "was it actually used" would need to
  ask whether a break occurred there, which the DOM does not expose
  directly. The checks above ask the coarser, still spec-accurate,
  question — "does the display contain at least one/two/three soft
  hyphens" — because every word this test data offers a soft hyphen to
  is, by construction (measured wider than the pane), one where the
  browser has no choice but to use at least one of them; a truly
  borderline word, wide enough to be offered a hyphen but in practice
  never using it, is not part of this test data and would need a
  different kind of check (reading computed line boxes) were one added.
- **The growing/shrinking-word check uses 66 characters of growth, not
  a smaller number.** The sixty-letter title item is already known
  (empirically, at both orientations) to force a split; the check needs
  a comfortable margin above that threshold in the *wider* of the two
  panes it must work in (landscape's right pane is the wider one), so
  the appended text is `'erandlonger'.repeat(6)` — 66 characters — and
  the Backspace count that undoes it is the same number, both computed
  once and reused, so the two can never drift apart by a miscount.
- **Paste and cut are not driven; a replacement stands in for them**,
  as in implementations 1 through 3, for the same reason (the clipboard
  is not reachable from a `file://` page under Playwright without
  permissions the origin cannot hold).
- **The message-truncation and message-list-scrolling checks read
  computed style, not an observed truncation or scroll**, for the same
  reason as implementation 3: no message this implementation produces
  is wide enough, and three messages do not overflow the panel.
- **The on-screen keyboard is not checked**, headless Chromium having
  none; it is a checkpoint row.
- **The checks were mutation-tested before being trusted.** Three
  deliberate faults were introduced into a scratch copy of the
  implementation, each targeting one of this implementation's own
  behavior changes: comparing only the title when sorting (instead of
  entire content) broke 2 checks
  (`orderComparesEntireContentNotJustTitle` in both orientations);
  reintroducing the "No messages" placeholder row broke 6
  (`messageListOpensEmpty`, `loadedStrippingIsSilent`, and
  `messagesNotKeptAcrossSessions`, in both orientations); and disabling
  `hyphenate()` entirely broke 8
  (`rightPaneSplitsWideWordWithHyphen`,
  `wordSpanningSeveralLinesHyphensEverySplit`,
  `longUnbrokenRunHyphensEveryLineItSpans`, and
  `growingWordGetsSplitAsTyped`, in both orientations). Each fault was
  reverted before the next was introduced; none was left in place.

## Regenerating the script

1. Read the use cases the implementation record includes and the record
   itself; draft the acceptance-criteria table.
2. For each row, write one or more named boolean checks; keep the two
   sequences above (or a new one that is written down before coding).
3. Confirm the hooks table against the implementation; add hooks to the
   implementation rather than locating by position. Where the record's
   test data can put two ideas in the same visible state (the two
   "Same first line" ideas; any idea once loaded three times), decide
   for each check whether "any matching row" or "this exact idea" is
   needed, and use `data-id` for the latter.
4. Run at every viewport the record's environment implies; review the
   screenshots once; report results faithfully.
5. Before trusting a passing run, break the implementation in a scratch
   copy in two or three ways the checks are supposed to catch —
   preferably ways that exercise what changed since the last
   implementation — and confirm the run fails, naming the checks.
