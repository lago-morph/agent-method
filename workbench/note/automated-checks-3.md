The specification from which `implementations/3/verify.js` can be
regenerated by an agent with no other context, and the decisions made
while writing it. The script is derived from this note, not the other
way round; when they disagree, this note is corrected first and the
script regenerated. The guide for notes of this kind is
[note/test-method-definition.md](test-method-definition.md).

Implementation 3 covers two use cases as revised on 2026-09-05, so the
checks cover both: [use-case/initial-ui.md](../use-case/initial-ui.md)
and [use-case/edit-ideas.md](../use-case/edit-ideas.md).

## Environment and harness

- **Runtime:** Node.js with Playwright and a Chromium build (any recent
  version; 1.56.1 and Node 22 were used). WebKit is preferred whenever
  it can be installed, because the target is Safari; Chromium is the
  stand-in, and the gap is stated in the report.
- **Loading:** the implementation file is opened over `file://` from the
  script's own directory, exactly as the user opens it. No server, no
  bundling, no copying.
- **Viewports:** two browser contexts, iPad landscape 1024 × 768 and
  iPad portrait 768 × 1024, both with touch enabled and mobile emulation
  on. Every check runs in both; a check that passes in one and fails in
  the other fails the run.
- **Errors:** a page-error listener is installed before navigation; any
  uncaught script error fails the run and is printed.
- **No test framework.** One plain script, no dependencies beyond
  Playwright, mirroring the implementation's own no-dependency rule.
- **Two sequences per orientation**, separated by a fresh page load:
  sequence A exercises the Initial UI use case, sequence B the Edit
  ideas use case. They share one browser context and one page; the
  reload gives sequence B a known starting state.
- **Three inspection checks** read the implementation's source text
  instead of driving the page, and are reported once, outside the two
  orientations.

## Hooks the implementation must expose

the contract between the implementation and the checks: an
implementation regenerated from the spec must expose them, or the checks
must be regenerated with it.

Rows are found by their exact visible text when a specific test idea is
needed; that is why test-data titles are stable. Rows named by text are
taken as `nth=0` of the matching rows, because three loads put three
copies of each test idea in the list; ordering among equal titles is
creation order, so `nth=0` is always the copy from the first load, and
the same row is found again after it is edited.

## Inspection checks

Run once against the text of `idea-workbench.html`, not against a page,
and reported under `inspection`.

| Check | Rule | Source |
| --- | --- | --- |
| `noClipboardCode` | the file matches none of `navigator.clipboard`, `execCommand`, or a listener for `copy`, `cut`, or `paste` | Edit ideas: the platform's standard facilities, no facilities of its own |
| `noExternalReferences` | the file matches none of `http://`, `https://`, `<script src=`, `<link`, `fetch(`, `import(` | Record: opened directly, no server, no build, no dependencies |
| `noPersistence` | the file matches none of `localStorage`, `sessionStorage`, `indexedDB`, `document.cookie` | Record: memory only; Initial UI: messages are not kept across sessions |

## Output contract

- One JSON object on standard output: `{ inspection: { check: boolean,
  … }, landscape: { … }, portrait: { … } }`, with an `errors` array
  added to an orientation only when script errors occurred.
- Then one line, `PASS` or `FAIL: ` followed by the failed check names
  as `group.check`, then one line naming the screenshot directory.
- Exit code 0 on pass, 1 on any failure.
- Screenshots go to the directory given as the first argument, or a
  fresh temporary directory; never into the repository.
- The script's header comment carries the run command:
  `NODE_PATH="$(npm root -g)" node verify.js [output-dir]`.

## Decisions made while writing the checks

- **The environment decisions of implementations 1 and 2 are repeated
  unchanged:** Playwright with Chromium (the only engine installed),
  loading over `file://` from the script's directory, both iPad
  orientations with touch and mobile emulation, exact expected counts,
  location by ids and classes with test ideas found by exact title,
  named booleans with a JSON body and a PASS/FAIL line, screenshots kept
  outside the repository, the page-error listener installed before
  navigation, a fresh browser context per orientation, two sequences
  separated by a reload, the keyboard rather than the buttons driving
  Undo and Redo, the insertion point placed with `setSelectionRange`
  rather than by clicking, and a run by hand before delivery. Their
  reasons are in [note/automated-checks-1.md](automated-checks-1.md)
  and [note/automated-checks-2.md](automated-checks-2.md) and are not
  restated here.
- **The three "by inspection" criteria became checks in the script.**
  Implementations 1 and 2 settled them by a person reading the file. A
  pattern match over the source text is weaker than a reading and could
  miss clipboard code written another way; it is used anyway because it
  runs on every run and catches a regression, and the weakening is
  recorded in [note/test-method-3.md](test-method-3.md).
- **Paste and cut are not driven; a replacement stands in for them.**
  The clipboard is not reachable from a `file://` page under Playwright
  without granting permissions the origin cannot hold. Typing over a
  selection takes the same code path in the implementation — one atomic
  change — and the use case treats a replacement as one change "like a
  paste" (edge case 19), so step 20 exercises the path and the real
  clipboard is a checkpoint item.
- **`strippingLeavesNoUndoEntry` needed a change to undo past.**
  Checking that undo returns "mango sorbet" after typing a space at the
  start proves nothing, because the same value is the text at selection.
  A "!" is typed first, so the single undo must reach past the stripped
  space to the "!" — and would fail if the strip had left an entry.
- **Undo grouping is checked at both ends of the rule.** Step 22 checks
  that six backspaces spanning one unit and its leading space are one
  change; step 23 checks that the seventh, which reaches the previous
  unit, is another. Steps 24 and 25 do the same for typing: the run ends
  where whitespace begins, and the whitespace goes with the text that
  follows it. These are the checks the use case's edge-case table exists
  for, and they are the ones most likely to break in a regeneration.
- **Undo and redo are pressed 40 times where the check is "all the way
  back".** The number only has to exceed the number of entries the
  typing produced (4); pressing more exercises "undoing at that point
  does nothing further" at the same time.
- **The caret-visibility check measures the scroller, not the caret.** A
  textarea gives no API for the caret's position, so the check scrolls
  the control back to the top with the caret at the end, types, and
  requires that what remains below the visible area is no more than the
  bottom padding plus one line.
- **The message-truncation check reads the computed style, not a
  truncated message.** The only message the implementation produces is
  short enough to fit at both iPad widths, so there is no way to observe
  the ellipsis. The three properties that produce it are checked
  instead, and the gap is stated rather than hidden.
- **The message-list scrolling check reads the computed style too**, for
  the same reason: three messages do not overflow a 60%-of-viewport
  panel. It also checks the panel is no taller than the window, which is
  the part that would break if the height cap were removed.
- **"A new message replaces the current one" is checked through a
  dismissal.** All the messages this implementation can produce have the
  same text, so replacement cannot be seen by watching the text change.
  Step 40 dismisses the current message and step 41 causes another, so
  the area going from empty back to the message, while the list grows by
  one, is the observable content of the rule.
- **`messagesNotKeptAcrossSessions` is driven, not inspected.** A reload
  is what "the application is closed" means for this interface, so the
  check reloads and looks at the list. The `noPersistence` inspection
  check backs it up.
- **The on-screen keyboard is not checked.** Headless Chromium has none;
  the behavior is a checkpoint row in
  [note/acceptance-criteria-3.md](acceptance-criteria-3.md).
- **The checks were mutation-tested before being trusted.** Three
  deliberate faults were introduced into a scratch copy of the
  implementation — never coalescing typed characters into a run,
  stripping trailing as well as leading whitespace, and keeping blank
  ideas that are not active — and the run was confirmed to fail, naming
  the checks each fault broke. A suite that passes on its first run
  proves nothing until it has been seen to fail.

## Regenerating the script

1. Read the use cases the implementation record includes and the record
   itself; draft the acceptance-criteria table.
2. For each row, write one or more named boolean checks; keep the two
   sequences above (or a new one that is written down before coding).
3. Confirm the hooks table against the implementation; add hooks to the
   implementation rather than locating by position.
4. Run at every viewport the record's environment implies; review the
   screenshots once; report results faithfully.
5. Before trusting a passing run, break the implementation in a scratch
   copy in two or three ways the checks are supposed to catch, and
   confirm the run fails.
