Captured 2026-09-05 at Jonathan's direction, after the checks had been
written: the specification from which `implementations/1/verify.js`
can be regenerated by an agent with no other context, and the
decisions made while writing it. The script is derived from this
note, not the other way round; when they disagree, this note is
corrected first and the script regenerated. The guide for notes of
this kind is [note-test-method-definition.md](note-test-method-definition.md).

## Environment and harness

- **Runtime:** Node.js with Playwright and a Chromium build (any
  recent version; 1.56 was used). WebKit is preferred whenever it can
  be installed, because the target is Safari; Chromium is the
  stand-in, and the gap is stated in the report.
- **Loading:** the implementation file is opened over `file://` from
  the script's own directory, exactly as the user opens it. No server,
  no bundling, no copying.
- **Viewports:** two browser contexts, iPad landscape 1024 × 768 and
  iPad portrait 768 × 1024, both with touch enabled and mobile
  emulation on. Every check runs in both; a check that passes in one
  and fails in the other fails the run.
- **Errors:** a page-error listener is installed before navigation;
  any uncaught script error fails the run and is printed.
- **No test framework.** One plain script, no dependencies beyond
  Playwright, mirroring the implementation's own no-dependency rule.

## Hooks the implementation must expose

The checks locate elements by these ids and classes. They are part of
the contract between the implementation and the checks: an
implementation regenerated from the spec must expose them, or the
checks must be regenerated with it.

| Hook | Meaning |
| --- | --- |
| `main > .pane` | the three panes, in order left, middle, right |
| `#left`, `#middle`, `#right` | the left pane, the idea list pane, the idea text pane |
| `#ideas li` | one row per idea, in display order |
| `#ideas li.empty` | a row showing the "(empty)" placeholder |
| `#ideas li.selected` | the selected row |
| `#text` | the element holding the selected idea's literal text |
| `#load-test-data` | the load-test-data control |

Rows are found by their exact visible text when a specific test idea
is needed; that is why test-data titles are stable.

## The checks, in sequence

State carries from one step to the next, so the order is part of the
specification. Expected counts follow from the test data set: 19
ideas per load (15 short, 1 wide, 1 large, 1 empty, 1 whitespace-only),
with the empty idea created before the whitespace-only one within a
load. Each check is a named boolean; the name states the expected
fact, so a failing name reads as the broken sentence.

| # | Step | Check | Source (use case or record) |
| --- | --- | --- | --- |
| 1 | page loaded, nothing done | `threePanesLeftEmpty`: exactly three panes; the left one has no text | Layout |
| 2 | " | `noIdeasListEmpty`: zero rows | Idea list: no ideas |
| 3 | " | `noSelectionTextBlank`: `#text` is empty | Idea text: blank when none selected |
| — | screenshot `0-empty` | | |
| 4 | click load once | `oneLoadGivesFullSet`: 19 rows | Test data: fixed set |
| 5 | " | `emptiesFirstAndGreyed`: rows 1–2 have class `empty` and text "(empty)"; row 3 does not | Empty ideas: placeholder, sorted first |

## Output contract

- One JSON object on standard output: `{ landscape: { check: boolean,
  … }, portrait: { … } }`, with an `errors` array added to an
  orientation only when script errors occurred.
- Then one line, `PASS` or `FAIL: ` followed by the failed check names
  as `orientation.check`, then one line naming the screenshot
  directory.
- Exit code 0 on pass, 1 on any failure.
- Screenshots go to the directory given as the first argument, or a
  fresh temporary directory; never into the repository.
- The script's header comment carries the run command:
  `NODE_PATH="$(npm root -g)" node verify.js [output-dir]`.

## Decisions made while writing the checks

- **Playwright with Chromium**, because that is what the working
  environment had installed; WebKit would have matched the target and
  is preferred when available.
- **Load over `file://` from the script's directory**, so the checks
  exercise the exact way the user opens the file and never drift from
  it by copying or serving.
- **Both iPad orientations, with touch and mobile emulation**, because
  layout differs between them and the target is touch.
- **Exact expected counts (19, 57)** rather than "more than before":
  the test data set is fixed, so the counts are known and a wrong
  count is a real finding.
- **Locate by ids and classes, find test ideas by exact title.** Ids
  and classes are stable hooks; titles are stable by the test-data
  rule. Nothing is located by position on screen.
- **Named booleans, JSON, PASS/FAIL line, exit code**, so a human
  reads the run and a script can too.
- **Screenshots at four named points, kept outside the repository:**
  evidence for a one-time visual review, not a deliverable; binary
  churn in the repository is not wanted.
- **The page-error listener is installed before navigation**, so
  errors during load are caught, not only errors during interaction.
- **Full sequence per orientation, in a fresh browser context each**,
  so orientations cannot contaminate each other.
- **Run by hand before delivery**, not in continuous integration:
  the repository has none, and the checkpoint is a person anyway.

## Regenerating the script

1. Read the use case(s) the implementation record includes and the
   record itself; draft the acceptance-criteria table.
2. For each row, write one or more named boolean checks; keep the
   sequence above (or a new one that is written down before coding).
3. Confirm the hooks table against the implementation; add hooks to
   the implementation rather than locating by position.
4. Run at every viewport the record's environment implies; review the
   screenshots once; report results faithfully in the PR.
