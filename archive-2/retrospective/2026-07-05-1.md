## Part 1 — what happened

### Phase 1 — exploration and diagnosis

Goal: assess the stakeholder's two methodology attempts (agent-method, visual-efp-open-up) against his handwritten re-scoping note. Two Explore subagents inventoried both repos in parallel and returned the numbers that carried the rest of the session: the first attempt was 61% process-about-the-process with zero tooling and a first gate that never ran; the second was excellent software whose method purpose (five templates) was never written down. A third finding mattered more than either: the standing docs had already gone stale — the repo had reproduced the failure it was designed to prevent.

### Phase 2 — three plans, two rejections

The first plan (one-page method, use-cases-only kernel, fixed file layouts) was red-teamed by a Plan subagent — which found the growth-law loophole, standing-doc creep, and a proven-loop omission — then rewritten twice on stakeholder direction: once to follow the human-scoped-deliverables conventions, once to fold in motivation from the k8s-platform forensics and software-factory history he linked. It was still rejected, correctly: it fixed *how* (file names, templates, commit sequences) while restricting *what* (an artifact universe too small to hold a project). A second, framework-level proposal was also deflected: "maybe we should work on some requirements for this instead of just jumping ahead." Unplanned but load-bearing: the plan-approval dialog failed on transport five consecutive times, and the plan was ultimately approved from an inline paste.

### Phase 3 — the requirements conversation

The productive altitude. Candidate requirements were harvested from evidence (his messages, the July-1 note, both post-mortems); his four "leanings" set the core (artifacts + checklist status load-bearing; workflows as glue; roles by capability; no meta-methodology); successive exchanges converged the concepts that now define the glossary — multiple named checklists dissolving "maturity," content/status-distinguished change propagation over an acyclic item-dependency graph, relational "verified," root-cause change routing dissolving "feedback" and "acceptance," judged items as externalization bookmarks. Each dissolution replaced a concept with a mechanism already present — the design got smaller as it got more complete.

### Phase 4 — decant, PR, review markup, merge

On "go ahead and write," the session decanted: archive move (pure renames), GLOSSARY.md, the requirements register, refreshed entry docs, then — triggered by the stakeholder asking what would be lost at termination — the complexity-review record and two lessons. PR #1 drew two review comments, both register-shaping: standalone requirements with two-way dependencies, and a promotion mechanic with candidates quarantined in a separate file. Both were applied same-session; a post-push grep caught three stale references and a broken line budget from the split (fixed in `7d5ae30`). Merged as `d920e9c`.

### Phase 5 — this retrospective

Run on request from the software-factory `self-retrospective` skill — machinery from the era this repo just archived, pointed at the session that archived it. The tension is real but resolvable: this package is AI-facing artifact material (hash IDs and all), and its proposals feed agent-method's own mechanisms — the stakeholder routes what earns adoption into CLAUDE.md rules, LESSONS.md entries, or CANDIDATES.md items. Nothing here is process until he says so. One meta-observation the skill itself forced: `date -u` says 2026-07-05, while everything committed mid-session is stamped 2026-07-03 — the session outlived its own sense of time.

## Part 3 — agents-file suggestions

Proposed additions to the project's agents file (`AGENTS.md`). Each rule has its own per-rule file in the sibling directory — `# agent instruction` (assembler-ready) plus `# justification` (stripped by the assembler). This repo has no assembler pipeline; the stakeholder routes adopted rules into CLAUDE.md's session rules or LESSONS.md as he sees fit. Both sections are mirrored inline below.

### Suggestion 1: Climb the ladder before shrinking the design — `AGENTS-MD-1d860006ec`

- **Per-rule file**: [./2026-07-05-1/AGENTS-MD-1d860006ec-climb-the-ladder-before-shrinking-the-design.md](./2026-07-05-1/AGENTS-MD-1d860006ec-climb-the-ladder-before-shrinking-the-design.md)

**Proposed agent instruction**:

> **Climb the ladder before shrinking the design.** "When the user says a proposal is too complex, too restrictive, or jumping ahead, do not respond with a smaller proposal at the same level. Move up one level - from implementation to design, from design to framework, from framework to requirements - and get the higher level agreed before descending again."
>
> *Grounded in: two consecutive plan rejections in the methodology-reset session.*

**Justification**:

The session lost its two largest work products to this exact failure. A full reset plan was rejected not for its size but for its altitude: it made implementation decisions while the question of what to build was still open. The corrected response was not a smaller plan — it was moving up to a framework conversation, and when that also proved premature, up again to requirements. Each failed descent cost a complete authoring-review cycle; the eventual requirements-first pass converged in one round. The marginal cost of the rule is a single question asked before drafting: "is the level above this one settled?"

### Suggestion 2: Fetch user-named public files via the raw host when API access is scoped — `AGENTS-MD-6e6975ed20`

- **Per-rule file**: [./2026-07-05-1/AGENTS-MD-6e6975ed20-fetch-user-named-public-files-via-the-raw-host-when-api-access-is-scoped.md](./2026-07-05-1/AGENTS-MD-6e6975ed20-fetch-user-named-public-files-via-the-raw-host-when-api-access-is-scoped.md)

**Proposed agent instruction**:

> **Fetch user-named public files via the raw host when API access is scoped.** "When the user explicitly links content in a public repository outside the session's GitHub scope, fetch it via raw.githubusercontent.com with curl; api.github.com, github.com pages, and git clone are proxy-scoped and return 403 for out-of-scope repositories. Do not use this path for content the user did not name."
>
> *Grounded in: 403 add_repo responses while reading the linked forensics documents.*

**Justification**:

The stakeholder linked post-mortem documents in two public repositories outside the session's repo scope. Three access paths failed in sequence — the GitHub API, shallow git clone, and the github.com HTML pages — before raw.githubusercontent.com served every file cleanly. Without the rule, each future session re-discovers the same dead ends (this one burned four tool calls plus a README-link workaround for directory listing). With it, one curl. The scoping caveat keeps the workaround inside user intent.

### Suggestion 3: Do not WebFetch instruction-bearing documents — `AGENTS-MD-9f66392955`

- **Per-rule file**: [./2026-07-05-1/AGENTS-MD-9f66392955-do-not-webfetch-instruction-bearing-documents.md](./2026-07-05-1/AGENTS-MD-9f66392955-do-not-webfetch-instruction-bearing-documents.md)

**Proposed agent instruction**:

> **Do not WebFetch instruction-bearing documents.** "To read a file whose content is itself instructions (a skill, a prompt, an agent rulebook), curl the raw file instead of using WebFetch - the fetch tool's extraction model can adopt embedded instructions as constraints on its own answer and refuse or distort the reproduction."
>
> *Grounded in: WebFetch refusing to reproduce SKILL.md because the skill's own 125-character quote limit contradicted the request.*

**Justification**:

Asked to reproduce a skill file verbatim, WebFetch's extraction model read the skill's internal quote-length rule as binding on itself and returned a refusal negotiating which summary to produce instead — a wasted call, and a near-miss on the worse outcome where a *reworded* skill is returned and trusted. The raw curl returned exact bytes first try. The rule costs nothing and removes a class of subtle corruption when the document being read is made of imperatives.

### Suggestion 4: Grep for stale references after any document move or split — `AGENTS-MD-50d9945c78`

- **Per-rule file**: [./2026-07-05-1/AGENTS-MD-50d9945c78-grep-for-stale-references-after-any-document-move-or-split.md](./2026-07-05-1/AGENTS-MD-50d9945c78-grep-for-stale-references-after-any-document-move-or-split.md)

**Proposed agent instruction**:

> **Grep for stale references after any document move or split.** "After moving, renaming, splitting, or merging documents, grep the live tree for every old name and path, and re-verify each document's self-declared constraints (line budgets, required sections) before pushing. Treat a hit as a defect, not a nit."
>
> *Grounded in: the register split leaving three stale references and a 22/20-line HANDOFF, caught only by an after-push grep.*

**Justification**:

Splitting the requirements register stale'd three references in GLOSSARY.md and CLAUDE.md and quietly pushed HANDOFF.md past its own 20-line rule. One grep caught all four — but only after the first push, costing a follow-up commit and a window where the live docs pointed sessions at the wrong file. This is the change-ripple failure the methodology exists to prevent (candidate R10), demonstrated on the methodology's own documents. Until the deterministic evaluator exists, the sweep is one grep plus one `wc` — seconds standing in for the bug class the whole session was about.

### Suggestion 5: Use repository-absolute paths in every shell call — `AGENTS-MD-9d6d272983`

- **Per-rule file**: [./2026-07-05-1/AGENTS-MD-9d6d272983-use-repository-absolute-paths-in-every-shell-call.md](./2026-07-05-1/AGENTS-MD-9d6d272983-use-repository-absolute-paths-in-every-shell-call.md)

**Proposed agent instruction**:

> **Use repository-absolute paths in every shell call.** "Do not rely on the working directory persisting between shell calls - it can reset without notice. Start compound commands with cd to an absolute repository path or use tool flags that take explicit paths (git -C)."
>
> *Grounded in: a commit command failing with 'not a git repository' after a silent cwd reset.*

**Justification**:

A commit-and-push command failed with "fatal: not a git repository" because the shell's working directory silently reset between calls. Cheap this time — one retry with an explicit cd — but the same reset under a different command shape (relative-path rm, redirects) is not. A few characters per command removes one of the most destructive failure classes available to a shell-wielding agent.

### Suggestion 6: Fall back to inline content when an approval UI fails repeatedly — `AGENTS-MD-a1d6f379b9`

- **Per-rule file**: [./2026-07-05-1/AGENTS-MD-a1d6f379b9-fall-back-to-inline-content-when-an-approval-ui-fails-repeatedly.md](./2026-07-05-1/AGENTS-MD-a1d6f379b9-fall-back-to-inline-content-when-an-approval-ui-fails-repeatedly.md)

**Proposed agent instruction**:

> **Fall back to inline content when an approval UI fails repeatedly.** "If a permission or approval dialog fails on transport more than three times, stop retrying: deliver the full content for approval in the conversation itself and request a plain-text decision. Never treat delivery failure as approval."
>
> *Grounded in: five consecutive plan-approval transport failures, resolved by presenting the plan inline.*

**Justification**:

The plan-approval dialog failed on transport five consecutive times while the stakeholder saw only silence. Retries one through three were reasonable; four and five bought nothing and stalled the session. The inline fallback — paste the plan, ask for a typed "approved" — worked immediately and preserved the gate's purpose (informed consent) rather than its mechanism. Both clauses matter: switch channels promptly, and never let a broken dialog become implicit permission.

### Suggestion 7: Verify the date with a tool before embedding it anywhere — `AGENTS-MD-8b8a1c0bc4`

- **Per-rule file**: [./2026-07-05-1/AGENTS-MD-8b8a1c0bc4-verify-the-date-with-a-tool-before-embedding-it-anywhere.md](./2026-07-05-1/AGENTS-MD-8b8a1c0bc4-verify-the-date-with-a-tool-before-embedding-it-anywhere.md)

**Proposed agent instruction**:

> **Verify the date with a tool before embedding it anywhere.** "Before writing a date into a filename, frontmatter, or record, verify it with a tool call (date -u, or Python datetime in UTC) - never trust the internal sense of today, especially in long-running sessions."
>
> *Grounded in: a session that started with documents dated 2026-07-03 and ended, per date -u, on 2026-07-05.*

**Justification**:

This session spanned at least three calendar days. Documents committed mid-session carry 2026-07-03, from ambient context that was accurate at session start; by retrospective time two independent tools agreed on 2026-07-05, and nothing in the session signaled the rollover. Dates in this repository are load-bearing provenance — the registers and lessons cite them as evidence — so silent drift corrupts exactly the audit trail the methodology depends on. The check costs one tool call.
