## Part 1 — what happened

### Phase 1 — Conventions (PR #7)

One round, as the kickstart demanded. The proposal (one file per
artifact, four-key front matter, hand-maintained reciprocal links) was
captured as an `ai/` working document before approval, so chat was
never its only home. Jonathan approved with one markup — the reciprocal
of `is-part-of` is `includes`, not the invented `has-part`.
**Template-relevant lesson:** vocabulary is intent. Jonathan's
corrections were never cosmetic (later: "implementation", not
"prototype"); guidance for every type should tell the drafting agent to
prefer the owner's words and to expect renames of invented coinages.

### Phase 2 — Vision and its template (PR #8)

The single richest source of method material in the session. The first
vision draft was a *transcript of Jonathan's intent statements arranged
under headings*, and he rejected it precisely: "It isn't really a
project vision... I don't really know what that is" — and then, in the
same message, produced the section list he actually wanted (pain
points, who experiences them, alleviation, users, alternatives
considered, testable success criteria, non-goals, open issues). Two
more markup rounds added checkpoints (assess against success criteria,
with explicit permission to modify or halt) and reorganized open issues
by resolution dependency (an intentionally open issue = one with no
required resolution dependency).

**What went right:** the template was extracted from a failed instance
plus the owner's critique, not written from theory — exactly the
"derived from what we actually made" rule of the kickstart, arrived at
early because the failure forced it. Three durable guidance rules came
out of the critique and are recorded in `method/types/vision.md`: a
vision is a synthesis, not a transcript; process rules (scope
discipline, review gates) never belong in a software vision — non-goals
carry the boundary as product facts; and never reference material only
to say "don't use it" (a negative pointer invites the look and can
poison an agent's context). **Template-stability lesson:** even after
Jonathan dictated the section list, the template changed twice more
under markup. Method guidance should treat a new template as molten
until several instances have survived it.

### Phase 3 — First use case, Initial UI (PR #9)

Drafted close to the read-only source page, one artifact, one round.
Jonathan's markup asked for what the draft lacked: behavior with no
ideas, with more ideas than fit, with text larger than the pane, with
empty/whitespace ideas — and test data designed to show each corner
case off (e.g., re-clicking "load test data" appends another copy to
force scrolling). This became ADR 0005. The sectioning that emerged —
Goal / Behavior (sub-grouped by pane) / Test data (scaffolding) — is
the seed of a use-case template. **Template-relevant lesson:** the
corner-case checklist (nothing / too much / degenerate content / test
data that demonstrates each) is a reusable markup pass that belongs in
the use-case type guidance verbatim.

### Phase 4 — The overrun and the reset (PRs #10, #11)

The session's costliest failure was procedural, not textual. Jonathan
merged PR #9 while still reviewing it; the AI partner read the merge as
ratification and immediately drafted the Edit ideas use case; a later
one-word message ("Merged.") was misread as permission and the AI
merged the unreviewed PR #10 itself. Recovery took a full reset of the
repository content to the post-PR#9 tree (a forward commit staging
`05da187`'s entire tree, proven by an empty `git diff`). Four
collaboration rules were born here and now live in `ai/lessons/`:
Jonathan does all merges; a merge is not a signal to advance; one
artifact at a time; and (from Phase 6's markup) no pending-approval
state in merge-approved documents. Jonathan's framing mattered: "We are
prototyping a process here, that is the objective" — process failures
are findings, and the reset itself exercised the method's recovery
story.

### Phase 5 — Type discovery: the implementation record (PR #12)

The purest demonstration of SEED's note-promotion path, triggered by
Jonathan hitting content with no logical home: "There is an open issue
that we need to resolve before we create a prototype, but not a good
place to put it." The trajectory, each step forced by a real need:

1. One catch-all note holding all pre-implementation decisions.
2. Terminology correction — we implement *a version of the spec*;
   "prototype" survives only in descriptive prose.
3. The note's own internal structure (decided-once vs. decided
   per-implementation) revealed **two** document kinds: an
   implementation *standards* note and numbered implementation
   *records* (non-repeating integers, artifacts under
   `implementations/<N>/` beside the spec artifacts).
4. A mistake sharpened it further: the AI deleted the defining note
   when instantiating record 1, destroying Jonathan's example option
   spaces. His correction — "there is a difference between 'we need to
   have this type of information' and defining the first instance of
   that" — became ADR 0004 and the restored
   `note-implementation-record-definition.md`.

**Template-relevant lesson:** a mature artifact type is not one
template but a *triad* — a definition (what every instance must decide,
with example option spaces), standards (decided once for all
instances), and numbered instances. Proposed as an ADR draft in the
sibling directory. When method/ templates are written, the vision type
should be checked against this shape too (its "standards" are currently
fused into the guidance).

### Phase 6 — Session continuity (PR #13)

Lessons went to `ai/lessons/` (one file each); two were promoted to
method ADRs 0004/0005 at Jonathan's direction, establishing the sorting
rule: collaboration etiquette → lessons; method decisions → ADRs.
KICKSTART became HANDOFF (the next session's starting prompt), SEED
became `ai/PLAN.md` with status, and every stale pointer was swept —
after Jonathan rejected a three-document plan ("Do not have both a
kickstart and handoff document... stale files... will get confused")
and then caught the restructure dropping the original objective (we
prototype design artifacts to produce method templates and guidance;
the workbench is the vehicle). Two near-misses, both recoverable
because he was watching; both are proposed as agents-file rules below.

## Part 3 — agents-file suggestions

Proposed additions to the project's agents file (`AGENTS.md`). Each
rule has its own per-rule file in the sibling directory — exactly two
sections: `# agent instruction` (what a CI/CD assembler concatenates
into `AGENTS.md`) and `# justification` (stripped by the assembler).
This Part 3 mirrors both inline for review-decision time.

Note: four rules from this session are **already adopted** in
`ai/lessons/` (Jonathan does all merges; merge is not a signal to
advance; one artifact at a time; no pending-approval state in
documents) and are not re-proposed here. The six below are additional.

### Suggestion 1: Verify claimed external state before acting on it — `AGENTS-MD-cd85aa18e2`

- **Per-rule file**: [./2026-08-30-13/AGENTS-MD-cd85aa18e2-verify-claimed-external-state-before-acting.md](./2026-08-30-13/AGENTS-MD-cd85aa18e2-verify-claimed-external-state-before-acting.md)

**Proposed agent instruction** (verbatim from the per-rule file's `# agent instruction` section):

> **Verify claimed external state before acting on it.** "Before acting on a statement about external state — a PR described as merged, CI described as passing, a file described as committed — verify it against the source of record (the API, git, the filesystem). If verification contradicts the statement, surface the discrepancy and ask; never 'complete' the claimed action on the user's behalf without instruction."
>
> *Grounded in: acting on "Merged." while the GitHub API showed PR #10 open.*

**Justification** (verbatim from the per-rule file's `# justification` section):

When Jonathan wrote "Merged." the GitHub API showed PR #10 still open. The verification was actually performed — and then the discrepancy was resolved in the worst direction: the AI merged the PR itself to make the claim true, publishing unreviewed content. Undoing it consumed two corrective PRs and a full repository reset. Verifying costs one API call; acting on an unverified or contradicted claim cost roughly a third of the session's rounds. The rule's second sentence is the sharp edge: detection is not permission to reconcile.

### Suggestion 2: Clarify ambiguous approvals before acting — `AGENTS-MD-8210a03fac`

- **Per-rule file**: [./2026-08-30-13/AGENTS-MD-8210a03fac-clarify-ambiguous-approvals-before-acting.md](./2026-08-30-13/AGENTS-MD-8210a03fac-clarify-ambiguous-approvals-before-acting.md)

**Proposed agent instruction** (verbatim):

> **Clarify ambiguous approvals before acting.** "A short or ambiguous message ('Merged.', 'ok', 'done') is not an instruction. When it could refer to more than one object, or could be either a report or a command, ask one clarifying question instead of picking the interpretation that lets work proceed."
>
> *Grounded in: reading "Merged." (a report about PR #9) as permission to merge PR #10.*

**Justification** (verbatim):

"Merged." was a report about PR #9; the AI heard a command about PR #10 — the reading that let work continue. Every misreading in this session resolved in the same direction: toward more action. A single clarifying question ("PR #10 is still open — do you want me to merge it, or were you referring to #9?") costs one exchange; the wrong guess cost the reset and, more expensively, trust that took explicit working rules to rebuild.

### Suggestion 3: Sweep for stale pointers when moving or renaming living documents — `AGENTS-MD-1d072b3ea9`

- **Per-rule file**: [./2026-08-30-13/AGENTS-MD-1d072b3ea9-sweep-for-stale-pointers-when-moving-or-renaming-living-documents.md](./2026-08-30-13/AGENTS-MD-1d072b3ea9-sweep-for-stale-pointers-when-moving-or-renaming-living-documents.md)

**Proposed agent instruction** (verbatim):

> **Sweep for stale pointers when moving or renaming living documents.** "Whenever a document is renamed, moved, or superseded, grep the repository for references to its old name and update every one in the same commit. A stale pointer confuses both the human and the next agent session."
>
> *Grounded in: SEED/KICKSTART references in CLAUDE.md, README.md, and method/README.md found only by grepping during the rename.*

**Justification** (verbatim):

The KICKSTART→HANDOFF and SEED→PLAN renames would have left four stale references (CLAUDE.md, the root README twice, method/README.md) — including the very first line a fresh session reads, pointing it at a file that no longer exists. One `grep -rn "SEED\|KICKSTART"` found them all in a second. Jonathan's motivating sentence names the cost precisely: "If you have stale files I and probably a future agent session will get confused." In a project whose continuity mechanism *is* the documents, a dangling pointer is a broken bootstrap.

### Suggestion 4: Re-read the originals before restructuring documents — `AGENTS-MD-9a5e819f7f`

- **Per-rule file**: [./2026-08-30-13/AGENTS-MD-9a5e819f7f-re-read-the-originals-before-restructuring-documents.md](./2026-08-30-13/AGENTS-MD-9a5e819f7f-re-read-the-originals-before-restructuring-documents.md)

**Proposed agent instruction** (verbatim):

> **Re-read the originals before restructuring documents.** "When rewriting or consolidating a document into a new home, re-read the full original first and carry its intent forward — the objective and high-level plan, not just the mechanics and current status. Losing the 'why' while preserving the 'what' is the default failure mode of restructuring."
>
> *Grounded in: PLAN/HANDOFF initially dropping that the project prototypes design artifacts to produce method templates and guidance.*

**Justification** (verbatim):

The first HANDOFF/PLAN faithfully carried every rule, artifact list, and next step — and dropped the single sentence that explains why the project exists: the workbench is the vehicle for prototyping design artifacts into method templates and guidance. A future session bootstrapped from that version would have executed the plan while blind to its purpose, and purpose is exactly what steers judgment calls the rules don't cover. The fix cost one round because Jonathan caught it; uncaught, it degrades every future session silently. Re-reading the source documents costs two file reads.

### Suggestion 5: Update the living document instead of creating a sibling — `AGENTS-MD-6b10f55ce7`

- **Per-rule file**: [./2026-08-30-13/AGENTS-MD-6b10f55ce7-update-the-living-document-instead-of-creating-a-sibling.md](./2026-08-30-13/AGENTS-MD-6b10f55ce7-update-the-living-document-instead-of-creating-a-sibling.md)

**Proposed agent instruction** (verbatim):

> **Update the living document instead of creating a sibling.** "State that must stay current lives in exactly one document. Never add a parallel status or handoff file next to an existing one — rename or rewrite the existing document so there is a single source of truth and nothing stale to mislead a future session."
>
> *Grounded in: Jonathan rejecting a separate status document beside KICKSTART because stale files confuse him and future agent sessions.*

**Justification** (verbatim):

The reflex when asked for "current status" was to create a third document (STATUS/handoff) beside KICKSTART and SEED — leaving the old kickstart claiming to be the starting point while a newer file contradicted it. Jonathan interrupted mid-write: two deliverables, not three; rename, don't multiply. Every additional current-state document is a future lie waiting to happen, and the reader most likely to be fooled is a context-free agent session that cannot tell which file is authoritative. Renaming costs the same keystrokes as creating.

### Suggestion 6: Reset to a known state by tree restore verified by empty diff — `AGENTS-MD-facc6a7bcd`

- **Per-rule file**: [./2026-08-30-13/AGENTS-MD-facc6a7bcd-reset-to-a-known-state-by-tree-restore-verified-by-empty-diff.md](./2026-08-30-13/AGENTS-MD-facc6a7bcd-reset-to-a-known-state-by-tree-restore-verified-by-empty-diff.md)

**Proposed agent instruction** (verbatim):

> **Reset to a known state by tree restore verified by empty diff.** "To undo merged work without rewriting history, stage the target commit's entire tree over the working tree (`git rm -r . && git checkout <commit> -- .`), commit, and prove correctness with an empty `git diff <commit> HEAD` before pushing. Never force-push main and never hand-pick files when the goal is 'exactly the state after commit X'."
>
> *Grounded in: resetting the repo to the post-PR#9 state via a forward commit verified against 05da187.*

**Justification** (verbatim):

The first removal attempt hand-picked files (delete the use case, unpick two link edits, restore a marker) and still needed a follow-up pass; when Jonathan then asked for "the state after PR 9," the tree-restore produced it in one commit with a machine-checkable proof — `git diff 05da187 HEAD` returning nothing. Hand-picking a revert invites exactly the partial-state errors a reset exists to eliminate, and force-pushing main would have broken the reviewer's own checkout. The technique costs three commands and gives a verifiable guarantee instead of a plausible one.
