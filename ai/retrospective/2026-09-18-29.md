## Part 1 — what happened

### Phase 1 — reading the queue

Jonathan opened by saying the queued work looked tedious and asked for thoughts, not action. The session read the handoff, the plan, the method plan from PRs #27 and #28, the lessons, the feedback document, and the latest retrospective in three batched reads; the first batch exceeded the output cap and was read back from the saved file in slices. The handoff turned out to be stale: it still named the implementation 4 checkpoint as the next step and did not mention the 22-step method plan that two later PRs had ratified. The first message reported that, then gave three assessments: the plan's cost was in the ceremony of 23 fresh sessions rather than in the writing; the halt rule was satisfiable by every step with the same aggregate measures; and steps 7 to 9 were one decision split in three.

### Phase 2 — the lifecycle

Jonathan described what he wanted: an implementation queued by editing its record, sealed by a commit that records the prep commit's hash, run without touching inputs, frozen with a log of issues, and inherited only by copying. The session accepted the shape and sharpened five points: the record as the manifest; the seal as two commits because a commit cannot contain its own hash; `input/` and `output/` directories so the boundary is visible by path; one log with three entry kinds; and a stop threshold, since runs 3 and 4 had each decided six or seven ambiguities and stopping on all of them would build nothing. Jonathan took all five and set the threshold at conflicts only, on the argument that a long list of logged decisions is what he wants to ratify from.

### Phase 3 — the decision log as the spec's engine

Jonathan then reframed the log: ratifying a decision means preserving it as a design artifact; a decision with no home goes in a note; clustered notes drive schema changes; the log therefore surfaces both what he wants locked and what he delegates. The session added the four fates (locked, delegated, reversed, left open), forward provenance (the absorbing artifact cites the frozen log entry), and the observation that the thirteen ambiguities already reported by runs 3 and 4 were a backlog on which to test the mechanism before implementation 5. It proposed that phase 1 of the plan shrink around this and asked for his word before touching a ratified plan.

### Phase 4 — locking in without hardening

Jonathan liked the direction, warned that trials propagate into rules, and asked for type descriptions only where the need was obvious, naming test data. The session proposed a trial ADR with a named exit event and a non-restatement sentence, three type descriptions, and four PRs in review order. He agreed and added one more thing to capture first: the imagined future workflow, in which the agent drafts artifacts and he works through conversation rather than PR review.

### Phase 5 — PR #29

The session wrote "The imagined workflow" into `ai/PLAN.md`, ADR 0008 in the existing ADR format with status Trial, a new phase 1 for `ai/method-plan.md` (nine steps and gate A; phase 2 kept its numbers with 11 to 14 unused; sixteen asserted substitutions patched phase 2's cross-references; one paragraph reflowed), and a new next-step block in the handoff. The PR was created, the PR number committed into the status table, and the recap stated no subscription existed. A `subscription.created` event then showed the harness had subscribed the session on creation; the session unsubscribed and corrected itself. The ADR came out at 725 words against the plan's eventual 150-word target for ADRs, which step 19 will handle.

### Suggestion 1: Check the entry document against the git log before starting — `AGENTS-MD-1bcc03b490`

- **Per-rule file**: [./2026-09-18-29/AGENTS-MD-1bcc03b490-check-the-entry-document-against-the-git-log-before-starting.md](./2026-09-18-29/AGENTS-MD-1bcc03b490-check-the-entry-document-against-the-git-log-before-starting.md)

**Proposed agent instruction** (verbatim from the per-rule file's `# agent instruction` section):

> **Check the entry document against the git log before starting.** Before acting on the handoff's "next step", compare it with the merged PRs since the handoff was last committed (`git log --oneline -- ai/HANDOFF.md` against `git log --oneline main`). If newer PRs changed the plan, say so in the first message and treat the newest ratified plan as current, not the handoff.
>
> *Grounded in: the 2026-09-17 session, where the handoff still named the implementation 4 checkpoint while PRs #27 and #28 had ratified a 22-step method plan it never mentioned.*

**Justification** (verbatim from the per-rule file's `# justification` section):

The handoff is rewritten at session end, but two PRs (#27, #28) landed a whole method plan without touching it. A session that trusted the handoff would have started on stale work, and the plan's own protocol tells each session to read only its step, so nothing downstream would have caught it. The check is one `git log` on the handoff and one on main, compared by date: under a minute. The cost of skipping it was, in this session, only avoided because the first instruction was to read everything; the plan's per-step sessions will not.

### Suggestion 2: Keep step numbers stable when replanning and leave gaps — `AGENTS-MD-474f93a45a`

- **Per-rule file**: [./2026-09-18-29/AGENTS-MD-474f93a45a-keep-step-numbers-stable-when-replanning-and-leave-gaps.md](./2026-09-18-29/AGENTS-MD-474f93a45a-keep-step-numbers-stable-when-replanning-and-leave-gaps.md)

**Proposed agent instruction** (verbatim from the per-rule file's `# agent instruction` section):

> **Keep step numbers stable when replanning and leave gaps.** When a ratified plan is restructured, never renumber steps that survive. Give new steps unused numbers, retire the old ones, and state the unused range in the preamble. Then grep the whole file for every old number in prose (`step 12`, `steps 17 to 20`) and patch each reference by an asserted substitution.
>
> *Grounded in: the 2026-09-17 phase 1 replan, which kept phase 2 at steps 15 to 21 and declared 11 to 14 unused.*

**Justification** (verbatim from the per-rule file's `# justification` section):

Retrospective 2026-09-09-27 already recorded a renumbering that broke cross-references across line breaks. This session avoided the problem by not renumbering: phase 2 kept its numbers, the retired range was declared, and only the twelve prose references that named replaced steps were patched, each by a substitution that asserted its anchor. Retrospectives, PR bodies, and chat all cite step numbers; a renumber silently invalidates every one of them. A gap in the sequence costs one sentence of explanation and nothing else.

### Suggestion 3: Every scripted substitution asserts its anchor — `AGENTS-MD-e29dcc2d4a`

- **Per-rule file**: [./2026-09-18-29/AGENTS-MD-e29dcc2d4a-every-scripted-substitution-asserts-its-anchor.md](./2026-09-18-29/AGENTS-MD-e29dcc2d4a-every-scripted-substitution-asserts-its-anchor.md)

**Proposed agent instruction** (verbatim from the per-rule file's `# agent instruction` section):

> **Every scripted substitution asserts its anchor.** When rewriting a document by script, express each change as `(old, new)` and assert that `old` occurs in the text before replacing it. A missing anchor aborts the run before any file is written. After the run, reflow any paragraph the substitution lengthened, and grep for the strings the change was meant to remove.
>
> *Grounded in: the method-plan rewrite of 2026-09-17, sixteen asserted substitutions over phase 2, one reflow, one stale-reference grep.*

**Justification** (verbatim from the per-rule file's `# justification` section):

A substitution that finds no anchor is a silent no-op: the file is written, the reference stays wrong, and nothing reports it. The assert turns that into a loud failure at zero cost, since the anchor text has to be written either way. The reflow matters too: one substitution in this session produced a 131-character line in a 72-column document, visible only because line lengths were checked afterward. Retrospective 2026-09-09-27's suggestion to rewrite all-or-nothing covers the transaction; this rule covers each step inside it.

### Suggestion 4: Unsubscribe from a PR right after creating it in this repository — `AGENTS-MD-d6d507d9f5`

- **Per-rule file**: [./2026-09-18-29/AGENTS-MD-d6d507d9f5-unsubscribe-from-a-pr-right-after-creating-it-in-this-repository.md](./2026-09-18-29/AGENTS-MD-d6d507d9f5-unsubscribe-from-a-pr-right-after-creating-it-in-this-repository.md)

**Proposed agent instruction** (verbatim from the per-rule file's `# agent instruction` section):

> **Unsubscribe from a PR right after creating it in this repository.** The harness subscribes the session to a PR the moment it is created, before any tool call of yours. In this repository, call `unsubscribe_pr_activity` for the new PR immediately after creation unless Jonathan has asked for a watch, and never tell him the PR is unwatched before that call has returned.
>
> *Grounded in: PR #29, told "not subscribed" and then found subscribed by a `subscription.created` event.*

**Justification** (verbatim from the per-rule file's `# justification` section):

The lesson caps PR watching at one hour because each wake re-enters the session with its whole context. In this session the recap said no subscription existed, then a notification arrived showing the harness had created one. The statement was wrong for a few minutes and cost one wake; had the session ended, the subscription would have run until the PR closed, exactly the overnight drain Jonathan described. One unsubscribe call after each PR creation removes the risk and makes the recap true.

### Suggestion 5: Commit the PR number into the plan's status table right after creation — `AGENTS-MD-8def809986`

- **Per-rule file**: [./2026-09-18-29/AGENTS-MD-8def809986-commit-the-pr-number-into-the-plan-s-status-table-right-after-creation.md](./2026-09-18-29/AGENTS-MD-8def809986-commit-the-pr-number-into-the-plan-s-status-table-right-after-creation.md)

**Proposed agent instruction** (verbatim from the per-rule file's `# agent instruction` section):

> **Commit the PR number into the plan's status table right after creation.** A step's PR number is not known until the PR exists, so a step's status row is completed in two commits: the step's content, then, after `create_pull_request` returns, one commit that fills the PR column. Do not guess the next number from the last one.
>
> *Grounded in: step 1 of the method plan, committed as `done` with an empty PR column and completed by a second commit naming #29.*

**Justification** (verbatim from the per-rule file's `# justification` section):

The status table is the one place a fresh session looks to find what happened to a step, and a row without its PR number sends the reader to the git log. Guessing the number from the previous PR fails whenever an issue or another PR takes the number first. The two-commit pattern costs one small commit and keeps the table right from the moment the PR is open.

### Suggestion 6: Record a trial decision with a named exit event and cite it only as a trial — `AGENTS-MD-8bed03ba2f`

- **Per-rule file**: [./2026-09-18-29/AGENTS-MD-8bed03ba2f-record-a-trial-decision-with-a-named-exit-event-and-cite-it-only-as-a-trial.md](./2026-09-18-29/AGENTS-MD-8bed03ba2f-record-a-trial-decision-with-a-named-exit-event-and-cite-it-only-as-a-trial.md)

**Proposed agent instruction** (verbatim from the per-rule file's `# agent instruction` section):

> **Record a trial decision with a named exit event and cite it only as a trial.** When Jonathan agrees to try a way of working but has not adopted it, record it as an ADR with status Trial that names the event at which he decides and the evidence he will weigh. Until that event, cite the ADR as a trial and never restate its content as a rule in a lesson, the handoff, a procedure, or a prompt.
>
> *Grounded in: ADR 0008 of 2026-09-17 and Jonathan's warning that "let's try it" propagates into "we must".*

**Justification** (verbatim from the per-rule file's `# justification` section):

Jonathan named the failure mode directly: a trial gets restated as a rule by the next document that mentions it, and nobody can find where it was decided. Lessons, handoff, and prompt templates are where it happens, because each one summarizes the others. The rule keeps one source, with a status line any reader can check, and makes the exit event a scheduled decision rather than a forgotten one. The cost is a status line and one sentence of discipline per ADR.

### Suggestion 7: In a discussion round, lead with the weakest points and then wait — `AGENTS-MD-73058c83ac`

- **Per-rule file**: [./2026-09-18-29/AGENTS-MD-73058c83ac-in-a-discussion-round-lead-with-the-weakest-points-and-then-wait.md](./2026-09-18-29/AGENTS-MD-73058c83ac-in-a-discussion-round-lead-with-the-weakest-points-and-then-wait.md)

**Proposed agent instruction** (verbatim from the per-rule file's `# agent instruction` section):

> **In a discussion round, lead with the weakest points and then wait.** When Jonathan asks for thoughts before doing, read the whole queue, then post: where the current state is wrong, where the plan is weakest, and what would reduce his cost, each in a sentence or two. Do not restate the plan, do not draft anything, and end the turn.
>
> *Grounded in: the 2026-09-17 session, which turned a plan Jonathan called tedious into one he called exciting in four exchanges.*

**Justification** (verbatim from the per-rule file's `# justification` section):

The previous planning session (retrospective 2026-09-09-27) took three plan versions to reach ratification, and Jonathan opened this session saying he had been putting the work off. Four discussion turns replaced fourteen phase 1 sessions with nine and produced the lifecycle he wanted, because each turn named a weakness and stopped. ADR 0002 already says discuss before delivering; this rule says what the discussion turn contains. Its cost is a full read of the queue before the first message.
